# cf-core-kit — Harness Parity Proposal (1:1 with backend-core-kit)

**Status:** draft for review (2026-10-12)
**Date:** 2026-10-12
**Revision:** r1 — initial 1:1 mapping of the family harness system
**Scope:** the harness system: verification profiles and lanes, gate sensors, the test harness, CI lanes and governance, knowledge/evidence/ledger machinery, task–workspace–handoff orchestration, doctor and scaffolding, and the harness documentation set
**Authority:** none — advisory design record; no implementation is authorized by this document
**Graduation:** on acceptance, the durable decisions distill into ADRs (`docs/adr/`) and the harness standards/engineering docs (`docs/standards/`, `docs/engineering/`), and execution moves to `docs/exec-plans/`

---

## 1. Summary

`cf-core-kit` mirrors `backend-core-kit`'s _product_ (contract, endpoints, budgets) but is deliberately thinner
in _harness_: 26 npm scripts against the family's 47, 1 CI job against 5, 6 normative standards against 15,
no execution-plan linting, no oracle registry, no gate-honesty meta-gate, no risk-aware CI lanes, no
episodes/diagnostics, no workspace worktrees, and a 5-check doctor against a 9-check one.

This proposal closes that gap **as a system, not as a pile of scripts**: every device in the family harness
gets a named 1:1 counterpart with the same responsibility, the same failure semantics, and the same policy
numbers where the regimes allow; the handful of devices that cannot translate (Docker-backed lanes, Prisma
drift, Nest DI stubs) get an explicit, reasoned replacement instead of silence. The proposal also adds a
mechanical parity checklist (`harness:parity`) so the 1:1 claim stays falsifiable after this work lands.

Recommended shape, in one line: **grow `tools/cfkit/` into the family's `tools/backendkit/` (same command
surface, same lanes, same taxonomy, same ledger discipline), keep our stronger stack-specific sensors, and
port the family's engineering-doc set so every mechanism has one documented home.**

## 3. Goals And Non-Goals

**Goals**

1. Every family harness device has a named 1:1 counterpart here, at the same layer, with the same failure
   semantics, or an explicit reasoned replacement.
2. Policy numbers from the family are either adopted verbatim or re-derived from _our_ measured baselines and
   recorded as such; no silent divergences.
3. The 1:1 claim is mechanically checkable (`harness:parity`), so it cannot rot.
4. Every mechanism has exactly one documented home; `AGENTS.md` stays a map, not a manual.
5. Nothing in the new harness may weaken an existing stronger sensor (our fatal duplication gate, strict
   budget rules, contract parity and provenance, zero-assertion rule).

**Non-goals**

- Changing the product surface, contract, or ADRs (ADR-0002 parity, ADR-0013 scope, ADR-0006 password descope
  all stand).
- Adopting the family's _team process_ wholesale (multi-agent scheduling, worktree-per-agent as a mandate).
  We port the mechanisms; the process docs state preferences, not obligations.
- Implementing the disabled improvement programme: we port its **gating** (empty ledger until eligible) so it
  stays disabled by construction, exactly like the family.
- Reaching the family's absolute script count: several of their scripts have no regime here (see §5.9).

## 4. Constraints And Invariants

1. **Free tier is architecture** (ADR-0005). Harness additions must not add per-request cost; the budget gate
   stays the authority. Nothing in this proposal runs inside the Worker.
2. **No external services in the default lanes.** D1, queues, DOs and R2 signing run under Miniflare; there is
   no Docker lane to mirror, and no `SKIP_DEPS_TESTS` escape hatch is needed.
3. **Gate honesty is a rule** (ADR-0011, roadmap): a gate that cannot fail is not a gate; every gate ships a
   probe or meta-test. This proposal _extends_ that rule to the whole harness via `verify:gates`.
4. **The contract is the family's** (ADR-0002): harness code never edits `contracts/` or invents operations.
5. **`src/platform` never imports features; features never import app entry modules; `src/shared` stays
   framework-free** (ADR-0008) — the harness mirrors these boundaries, it does not relax them.
6. **Zero assertions in `src/**`** and the crypto allowlist (ADR-0006) remain enforced; harness code may use
   assertions only inside `tools/`/`scripts/` where they are the subject of scrutiny.
7. **Advisory budgets stay advisory** until reviewed clean-runner observations justify otherwise.
8. **Harness state is git-ignored**: `.cfkit/**` (family: `.tmp/backendkit/**`); doctor asserts it.
9. **No secrets in evidence, ever** — redaction is structural (regex + caps), not editorial.
10. **The 1:1 parity list is the acceptance boundary**, not a count of files.

## 5. Proposed Design — The 1:1 Mapping

Legend: **F** = family component (path) · **O** = our current state · **T** = 1:1 target here · **N** = notes /
regime adaptation. Every row is a decision: to port, to replace, or to decline with a reason.

**Flow (target state).** One task, one plan, one lane — and the artefacts each phase owns:

```text
docs/exec-plans/active/<plan>.md          (metadata: Task ID, Risk/Max, Authority, Repair limit, timeout, impacts, allowed paths/actions)
        │
        ├─ plans:check ──────────────► plan contract valid · ≤1 active · status matches folder
        │
        ├─ cfkit task preflight ─────► authority hash match · action allowed · paths ⊆ Allowed paths · risk ≤ Maximum risk
        │
        ├─ cfkit ci classify ────────► effective_risk (path risk ∨ declared risk, raise-only)
        │                              ├── low  → lane fast   (static gates + unit)
        │                              └── else → lane full   (all static gates + coverage + duplication + build)
        │                                        └── + runtime when any impact reason matches (API/DB/auth/queue/config/external)
        │
        ├─ cfkit task verify ────────► profile run (fail-fast, durations, advisory budget)
        │        │                        ├─ pass → state ready_for_review (+ episode; reviewRequired when high)
        │        │                        └─ fail → taxonomy {code, remediation, repairable}
        │        │                                 ├─ repairable & attempts ≤ limit → repairing (fingerprint-counted)
        │        │                                 └─ else → escalated
        │        └─ artefacts: .cfkit/tasks/<id>/{state.json, episodes/attempt-N.json, diagnostics/attempt-N.txt ≤16 KiB redacted}
        │
        └─ cfkit handoff dry-run ────► approval (15 min, bound to fingerprint + workspace + branch + exact paths; only hash stored)
                 └─ commit (exact paths) · push (non-force) · draft-pr (no merge/deploy/ready/force)

CI mirrors the same lanes, and never inlines them:
  risk ──► full (verify:ci) ──► runtime (conditional on runtime_required) ──► governance (dependency review, secret scan, audit) ──► required (branch protection)
```

## 6. Consequences And Tradeoffs

**Positive**

- Risk-aware lanes + a real CI split turn "which verification applies" into data, and make the ledger and
  episodes meaningful; today every change runs the same profile, so the machinery cannot distinguish a docs
  tweak from an auth change.
- Failure taxonomy + gate honesty make failures actionable _and_ provably detectable; the repo's own
  "gate honesty" rule becomes enforced end-to-end rather than per-script.
- Oracles bind high-risk behavior to real-transport evidence, closing the one honesty gap we cannot currently
  falsify (a deleted integration suite would silently reduce coverage).
- Plan metadata + knowledge lint make the exec-plan corpus machine-checkable, which matters because our plans
  are the interface between people and agents.
- Episodes/diagnostics/ledgers give the harness memory without storing prompts, secrets or raw output.

**Costs and risks**

- **Surface growth**: ~15 new commands/scripts and ~15 new docs. Mitigation: every mechanism lands with its
  checker and its doc in the same change; `harness:parity` fails when one half is missing.
- **CI minutes**: five jobs on a free-tier GitHub account. Mitigation: `risk`-gated runtime lane, npm cache,
  `cancel-in-progress`, and the aggregate job keeps branch protection stable while runtime is skipped.
- **Ledger/plan discipline can become ceremony** if the numbers are wrong. Mitigation: keep every threshold
  advisory until a reviewed baseline exists (family policy), and record the baseline with its date.
- **Smells detector false positives** would leak into CI. Mitigation: baseline file + new-findings-only mode +
  `docsLink` per rule told reviewers _why_; authority to write baselines requires explicit approval env.
- **Mutation pilot cost**: seeded mutations re-run one spec file per mutation. Mitigation: two tiny pure files,
  ≤10 mutations, never in a profile.
- **Worktree machinery** can confuse a single-agent flow. Mitigation: `workspace prepare` is opt-in and the
  parallel-agent doc states the preference order (single tree → worktree → clone).

dependency-ordered. Each plan is one exec-plan file with its own tests and a `npm run verify`; each batch ends

**Critical path:** A1 → C10 → D14 → D15/D16 → F18 → F20. Everything else fans into it; the longest chain is six
plans, and batches A and B can run fully in parallel with each other once A1/A2 land.

**Consolidation options** (if you prefer fewer review units): A3 folds into A6 (the config sensor is the honesty
probe's prerequisite); B9 folds into B7 (one "test harness" plan); C13 folds into C10 + F18 (plan intake with the
plan contract; maintenance with the tooling plan). Each merge costs a larger single review, and none changes the
ordering or the exit gates.

**Execution rules for every phase**

1. Order inside a batch is free; the batch's dependency edges are not.
2. A mechanism never enters a profile before its fixture or meta-test exists (the gate-honesty rule, extended
   to the whole harness by plan 6).
3. Baselines are captured from the pre-change tree and recorded with their date: the smells baseline, the
   small-helper duplication allowlist, any coverage-floor or duration-budget re-baseline.
4. Documentation lands with its mechanism; plan 19 covers only the cross-cutting set (guardrails, cfkit
   reference, runtime-evidence, the loop/agent/parallel/hill-climbing docs, the index drift rules).
5. A1 creates the parity manifest and every later plan updates its own rows, so `harness:parity` is meaningful from batch A onward — rows
   may be `declared-only` until their plan lands, and must not be deleted to make the check pass.

**Entry conditions** (before batch A): the proposal is accepted; open questions 1 and 4 are answered (workspace
scope, mutation placement); the ADR-0013 scope commit has landed; ADRs are recorded for the pieces that change
baselines (task authority, risk-aware verification and repair, isolated workspaces, verified handoff, plan
contract, oracles and operating evidence — the family records the same set as ADR-0019…0026); and the smells
baseline is captured before the scanner can fail anything.

**Acceptance amendments required at execution start** (so no plan drifts outside the contract): add three
criteria to §8 — (13) the mutation pilot with its thresholds and its "never in a profile" policy; (14) workflow
conventions: PR template, dependabot, commitlint + hooks with the scope enum; (15) the doctor, scaffold and
events/maintenance command surfaces. Plans 9, 17 and 18/13 close them respectively.

**Explicitly not sequenced here:** the credentialed lanes (live deploy, dashboard CPU per route class, live R2
round-trip) — they need account access, not code; the improvement programme beyond its gating (disabled until
the ledger clears its eligibility thresholds); and anything outside the proposal's scope, including the
descoped `admin` / `merchantOnboarding` surfaces (ADR-0013).

**Abort and rollback:** every plan is additive tooling — no wire-contract, migration, or runtime change — so a
batch can be abandoned by removing its scripts and profile steps; the only durable artefacts are docs, ADRs and
the parity manifest, which is why `harness:parity` and the per-batch gates are the acceptance boundary.

## 8. Acceptance Criteria

The proposal is satisfied when all of the following hold, each verified by a named command or test:

1. **Command-surface parity** — `cfkit --help` lists every family command with a 1:1 counterpart (or an entry
   in §5.9); `tools/cfkit/cli.test.ts` asserts the surface and the 0/1/2 exit-code semantics.
2. **Profile + lane parity** — `profiles.test.ts` asserts registry invariants; `ci classify` reproduces
   `effective_risk`/`runtime_required` for fixture diffs, including raise-only behaviour and `unknown ⇒ medium`;
   a fixture proves every risk-rule prefix resolves to a real path (or is marked `planned`).
3. **Gate parity** — every gate in §5.2 exists as an npm script and is wired into exactly one profile;
   `harness:parity` asserts the gate list against a checked-in manifest.
4. **Gate honesty** — `npm run verify:gates` passes: each planted violation makes its wired gate fail with the
   expected marker, and cleanup restores the tree byte-identically.
5. **Oracle parity** — `oracles:check` passes with ≥ 6 entries, all backed by `test/integration/**` or
   `test/contract/**`; a fixture proves a unit-only or missing-file entry fails validation.
6. **Knowledge parity** — `plans:check` enforces the §5.5.1 contract; fixtures prove each failure mode
   (missing metadata, wrong folder status, duplicate task id, two active plans, unchecked box in `completed/`).
7. **Evidence machinery** — an episode + diagnostic are written by `cfkit task verify` for a forced failure;
   the diagnostic is ≤ 16 KiB, redacted, and the episode rejects a forbidden key (fixture).
8. **Ledger honesty** — `evidence check` passes on the empty ledger and fails on a fixture with a missing
   hash/approval/CI revision; `improve check|analyze|shadow` report `ineligible` while the ledger is empty.
9. **CI lane parity** — the workflow has `risk`/`full`/`runtime`/`governance`/`required`, the runtime condition
   string, the aggregate tolerance, SHA-pinned actions and `persist-credentials: false`; the extended
   workflow meta-test asserts all of it.
10. **Docs parity** — `docs/engineering/` exists with the §5.8 files; the drift check verifies both new indexes
    (engineering + standards) enumerate their directories.
11. **No regression** — `npm run verify:ci` stays green, coverage floors unchanged or raised, duplication core
    profile still fatal, contract parity/provenance untouched, bundle within budget.
12. **Parity is falsifiable** — `npm run harness:parity` compares the checked-in parity manifest
    (`docs/engineering/harness-parity.md` table) against the live tree (commands, scripts, gates, docs,
    ledgers, oracles) and fails on any missing or extra row.

## 9. Open Questions

1. **Scope of the workspace machinery** — port `task workspace prepare` fully, or document worktrees as the
   parallel-agent mechanism and implement it only when a second agent runs concurrently?
   _Recommended default:_ implement the lock + workspace manifest (small, prevents concurrent runs), defer
   `git worktree` until parallel work is real.
2. **Repair limit default** — family plans use 2, our current default is 3. _Recommended default:_ keep 3 as
   the fallback, require the plan to declare it explicitly (family behaviour).
3. **Smells rule set size** — start with the 10 rules listed in §5.2 row 2.5, or a smaller first tranche?
   _Recommended default:_ land all ten but ship with a baseline captured from the current tree, so CI fails
   only on new findings.
4. **Mutation pilot placement** — `tools/cfkit/**` (policy) is the family's choice; is that where our harness
   most needs assertion evidence? _Recommended default:_ start with the risk classifier + duration policy; add
   `src/platform/queue/defaults.ts` (backoff math) if the pilot proves cheap.
5. **Ledger promotion** — do we intend to ever promote entries, or keep the ledger as an honest empty record?
   _Recommended default:_ keep it empty until a human review process exists; the checker still runs.
6. **Governance secret scanning** — our tracked-file scan vs an action with history coverage.
   _Recommended default:_ add the action; keep our scan (different scope).
7. **`harness:parity` artefact form** — a markdown table (readable) vs a JSON manifest (precise).
   _Recommended default:_ JSON manifest + a generated markdown view, so the check is precise and the doc stays
   readable.
